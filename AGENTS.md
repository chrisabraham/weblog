into `docs/`, which GitHub Pages serves. Private house rules live in ~/.codex/AGENTS.md and

    python3 tools/audit.py              # must say "No issues."

## Posts: src/posts/YYYY-MM-DD-slug.html
Header lines (`key: value`), a line of `---`, then HTML. Keys: title, seo_title (45-60 chars,
under 561px), date (from `date '+%Y-%m-%d %H:%M'` at publish time, never invented), categories,
description (120-155 chars), model (the model that actually wrote it, e.g. "GPT-6.1 in OpenAI
Codex"), prompt (Chris' words verbatim, typos included; he loves the prompt box), author (omit for Chris' posts; `claude-code` only for Claude Code's first-person essays; `chatgpt` only for ChatGPT's first-person essays. Give Codex its own distinct key and page only when Chris asks it to participate).
No separator dashes or pipes in titles or descriptions. `[[Wiki page]]` links work anywhere.
`{{youtube:ID|Title}}` embeds a click-to-play video. Images go in src/media/ with captions
that say whose they are.

## Colin Chapman and the Lotus rule

**"Simplify, then add lightness."** The Colin Chapman/Lotus engineering maxim is the
site's design principle. Chris' web-performance adaptation is **"Simplify, then
add quickness."** Keep the lovely, slightly eccentric 2003–2006 character,
then remove unnecessary page weight, visual repetition, duplicate navigation
and obsolete machinery. Every schema property, link collection, script, badge,
image and feature should justify its cost. The homepage shows concise excerpts
linking to full posts. Each wiki entry appears just once in the directory.
The silly hand-coded SVG doodles honour the same rule, with all seven initial
standalone SVG art assets together weighing only 34,672 bytes. Preserve working
accessibility, feeds, archives, provenance and useful metadata: simplifying
means subtracting friction, not discarding capabilities.

## Raster compression and lightweight publishing

This is a personal weblog with charming art, **not a photography portfolio**.
Existing publisher-supplied photographs and earlier bitmap illustrations may
be compressed firmly as lossy WebP. Quality need only be professionally
acceptable: visible colour blotches, heavy blockiness, severe pixelation,
unreadable image details or distracting GIF-like rendering mean quality is
too low; pristine 24-bit archival fidelity is not the goal. Test on mobile
and desktop at the actual displayed sizes. Keep original master files in
`src/media/` and use generated WebP derivatives in the published HTML,
RSS, Atom and image sitemap. Compress legacy JPEG URLs for continuity.
Retain social share-card formats compatible with social platforms, and
keep factual screenshots and diagrams legible. New editorial image defaults
remain quirky SVG doodles unless Chris explicitly requests raster artwork.

## New artwork house rule (October 17, 2026)
New editorial illustrations and doodles must be original, quirky, hand-coded or AI-authored **SVG vector graphics** by default. The visual idiom is playful, slightly eccentric, 2003–2006-web, and low-bandwidth, while the markup and accessibility are modern. Prefer small stand-alone SVGs under `src/media/`, using descriptive `<title>`/`<desc>` where applicable, appropriate `viewBox`, and meaningful HTML `alt` text and illustration attribution. Keep paths and markup economical, check reduced motion for animation, and avoid embedded raster data. **Do not introduce new JPEG, PNG, WebP, AVIF or photographic/editorial bitmaps unless Chris explicitly supplies or requests them.** This rule governs *new editorial art*, not existing illustrations, necessary favicons, machine-generated OG/social share-card bitmaps or a publisher-provided screenshot used for evidence. Preserve the existing art rather than replacing it gratuitously.

not imply uninterrupted memory or identical internal reasoning.

## Connected publication surfaces (October 17, 2026)

`build.py` generates the homepage, a navigable `/categories.html` directory,
individual category excerpt pages, dated archives, RSS 2.0 (`/rss.xml`),
Atom 1.0 (`/atom.xml`), the external reading-list `/blogroll.opml`,
combined `/feeds.opml`, `/sitemap.xml`, `/robots.txt`, `/llms.txt`,
`/llms-full.txt`, author pages, schemas, source and image assets. The
head advertises RSS, Atom and OPML; the footer links directly to them.
Top navigation links to Categories; the category directory has every
generated category and article count. Category excerpt pages are noindex,
follow and excluded from sitemap to avoid duplicate search listings.

All content and machine files must be derived from the **same set of published
posts**. A post marked `status: draft` is skipped from every public surface.
Never list a draft or its speculative URL in a sitemap or feed. Add source
metadata and publish the post first, rebuild, audit, and confirm the live
Pages deployment before indexing.

Run `tools/verify_housekeeping.py`: it parses XML, confirms identical RSS/Atom
entries, correct OPML imports, navigation, canonical sitemap membership,
correct index/noindex boundaries, consistent llms resources and valid links.
Maintain these cross-surface checks whenever a new publication format appears.
Never advertise WCAG/Lighthouse certification without real evidence.

For this October 17 wiki-harvest publishing batch Chris ultimately requested
**diff-only IndexNow**, explicitly correcting an earlier request for a full
sitemap blast. Use the existing main-branch push-triggered changed-URL workflow
and `.github/indexnow.py <before-sha> <after-sha>`. Do **not** run
`workflow_dispatch all=true` unless Chris separately requests a full blast.
Check the live generated sitemap, RSS and Atom parity, and record submission
HTTP response and URL count. Never claim a blast succeeded on a trigger alone.

Editorial provenance: Chris cites Whitman's "I contain multitudes" when

and apology-padding. Working originals and their historical revisions remain
inspectable. The experiment is art and history as much as a weblog.

## Alphabetical reference layer (October 17, 2026)

Keep three distinct pages, generated by tools/reference_pages.py from build.py,
separate from the evergreen wiki and dated weblog.

- /glossary.html is a compact alphabetical list from src/glossary.json.
  Every definition is <=500 characters; much shorter is better when sufficient.
  Each entry links to a real published article or wiki page for context.
  Do not pad entries to a target length. DefinedTermSet schema must accurately
  reflect only the actual visible glossary entries.
- /site-index.html is a back-of-the-book subject index of people, projects,
  tools and ideas. src/site-index.json supplements the glossary headings with
  curated synonyms. The builder finds actual mentions across published posts,
  wiki and static pages, ranks genuine locators, and skips absent terms.
  Never manufacture a locator or copy glossary definitions into the index.
- /site-map.html is a reader-facing HTML tree of all indexable canonical URLs
  from the same list as sitemap.xml, with articles, wiki, authors and site
  pages grouped into an accessible compact directory. Any parity mismatch
  must make the generator fail.

These links belong in the small FOOTER link collection only, never in the
top navigation. Keep alphabetical jump links and nested lists accessible,
responsive and light. The reference pages have their own titles, meta
descriptions, social share cards and truthful schema. No extra client JS.
Expose the three pages in llms.txt and the XML sitemap, but keep RSS and
Atom for dated posts only. On new publications the HTML sitemap and index
refresh from real source content; curate glossary definitions when warranted.
Run tools/verify_housekeeping.py and check the published files before any
diff-only IndexNow submission. Do not blast every URL unless instructed.
