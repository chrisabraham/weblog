Narrator: Yesterday I showed my new weblog to somebody on Mastodon. I pitched chrisabraham.net as a return to the internet circa 2006. Nash Ricky replied, “2006 internet was better internet.” When I asked him what he thought of the site, he told me it looked nice and that he wanted something like it for himself. He mentioned Blogspot, the old Google blogging service, and explained that he mostly wanted somewhere to document his life and write a journal. Sharing it with the world was optional.
Narrator: It occurred to me that the most useful thing I could publish next was a set of instructions. If you can describe the sort of website you want, you can ask an AI coding assistant to help make it. You can have your own address on the web, an archive, old-fashioned links, your own colours, and somewhere to write. You can make the thing wonderfully personal. You needn't learn an entire programming language before you begin.
Narrator: The design brief I eventually settled on is an automotive one. Think of an ICON 4x4 restomod: the body and temperament of a 2003 or 2004 machine, with a 2026 chassis, engine and brakes. My weblog has that early-blog look. Underneath it are responsive layouts, accessible markup, modern publishing automation, structured data, feeds, and rather more inspection machinery than most personal websites will ever need.
Narrator: Fortunately, you do not need to be remotely as persnickety as I am. Begin with a personal homepage and one post. The rest can arrive when you fancy it.
Narrator: First, what I actually built
Narrator: The source code is public at github.com/chrisabraham/weblog. Please inspect it, copy the ideas, and notice the important thing: my site does not use Jekyll. Jekyll is one of many programs that assemble pages from content and templates. It's a perfectly respectable choice. I originally mentioned it because I knew it was associated with GitHub Pages. The weblog itself uses a custom Python script called build.py.
Narrator: That Python program reads articles from src/posts/, wiki entries from src/wiki/, images from src/media/, and site settings from src/site.json. It uses templates and src/style.css to generate finished HTML pages in docs/. GitHub Pages serves the resulting HTML, CSS, pictures, and feeds. Nobody visiting the finished website needs to run Python. In fact, there is no Python application running on GitHub Pages when you open an article in your browser.
Narrator: your-repository/ build.py src/ posts/ 2026-10-17-my-first-post.html wiki/ getting-started.html media/ my-picture.svg style.css docs/ index.html ...generated pages... .nojekyll .github/ workflows/ site-build.yml That's a sketch of the idea, not a file-for-file copy of my rather elaborate repository. The source is your workshop. The docs/ directory is the finished car. You change things in the workshop and let the builder produce the car again. My repository uses GitHub Actions to run the builder and publish the generated files. A beginner can choose a simpler GitHub Actions deployment instead of committing an entire generated docs/ folder.
Narrator: If you want a real example, open my builder and the posts folder. It is a functioning publishing system, with decades of weblog culture baked into its appearance and a rather contemporary obsession with making everything inspectable.
Narrator: What you need before asking AI to build anything
Narrator: A GitHub account. Sign up at github.com. GitHub stores your website files and remembers each change, so you can recover an earlier version.
Narrator: An AI coding assistant. Claude Code or OpenAI Codex is the most direct route for asking a machine to edit a repository. You can also begin in ChatGPT or ordinary Claude chat and copy the generated files yourself.
Narrator: A name. A weblog title, a short description, and perhaps three favourite colours will do. A custom domain is optional.
Narrator: One thing to say. You can write a diary entry, a book note, a project update, or your thoughts about a particularly offensive modern website.
Narrator: On GitHub, create a public repository named YOURUSERNAME.github.io, replacing YOURUSERNAME with your GitHub username. This special name gives your personal GitHub Pages site a convenient address: https://YOURUSERNAME.github.io/. Add a README when GitHub offers one. A public repository works on GitHub's free Pages tier; keep secrets, private journals and passwords out of it. You can make another repository name work too, but then its normal address includes the repository name as a path, which makes an easy starter lesson needlessly awkward.
Narrator: Which AI can talk to GitHub?
Narrator: This is where people get tripped up, because the names of the chat products and the coding agents overlap.
Narrator: ToolWhat it can do for your weblog Claude Code in a terminalWork in a local checkout, create and edit files, run the build, and use Git to commit or push when you approve access and actions. Claude Code on the webAt claude.ai/code, use an authorized GitHub repository in a cloud coding session; it can make changes and prepare a pull request to review. Ordinary Claude chat on the webRead selected GitHub repository files through its integration and help plan, explain or draft changes. Do not assume that selecting a repository in a normal chat gives it the same write-and-publish powers as Claude Code. OpenAI CodexWork on repositories through its coding workflows, make changes, run checks and prepare code changes or pull requests where the connection and permissions allow. ChatGPTDraft copy and code and, in some connected or agent-enabled environments, perform supported repository actions. Its ordinary GitHub reading connection is not itself a promise of write access. Check the tools and permissions actually available.
Narrator: The safest habit is to let the machine propose a change, inspect its diff, run a build, and only then merge or deploy. Authorize the specific repository you intend to use. A GitHub connection to read your code and a coding agent permitted to write code are different privileges.
Narrator: Step one: describe the website you want
Narrator: Start with the visual identity. I would say something like this. Paste the following into Claude Code or Codex with your new repository selected, or use it in ChatGPT to get the initial files.
Narrator: Prompt 1: Build my personal weblog. Help me build a personal weblog inspired by independent websites from 2003 and 2004. I want a restrained, personal, old-school design with a site title, a short introduction, a latest-posts index, individual dated articles, an archive, an About page and ordinary blue-underlined links. Think early Blogger, personal homepages and RSS-era weblogs, with a 2026 engine. The design must be fully responsive on phones, keyboard accessible, screen-reader friendly, and readable when JavaScript is disabled. Use semantic HTML, simple CSS and a small Python 3 static-site generator. Put my editable content in src/. Publish finished files as a static site using GitHub Pages and GitHub Actions. Keep dependencies minimal and explain the structure to me like I am a beginner. Do not install a giant framework or invent advanced features. Show me a working first page.
Narrator: Tell the assistant what you like. “A serif body font and orange headings.” “A narrow column because I want it to read like a letter.” “More like a 2004 Movable Type blog.” “Keep the archives prominent.” If you have an existing blog, ask it to preserve your URLs and links. If it shows you something you dislike, tell it what you dislike. You are allowed to be the creative director of your own bloody website.
Narrator: Step two: make the source files and a builder
Narrator: Ask the coding agent to create a simple build.py program that reads posts and writes HTML pages to a public output directory. At the beginning you only need build.py, src/style.css, and one file in src/posts/, plus the publishing workflow the agent creates. You can have it store posts as Markdown or as basic HTML with a few metadata lines. My own posts use a small header, a line containing three hyphens, and ordinary HTML afterward.
Narrator: title: My first weblog post date: 2026-10-17 10:00 categories: Journal description: The first entry on my new personal weblog. --- <p>Hello, internet. I have a home here now.</p> The date above is only an example. Use the actual date and time when you publish. If the coding agent chooses Markdown instead, that is fine. There is no sacred post format.
Narrator: Prompt 2: Make the publishing engine. Implement the smallest sensible Python builder for my weblog. Read dated posts from src/posts/, escape metadata safely, generate an HTML homepage with one-paragraph teasers, generate a separate permalink page for every full article, and make an archive page. Use one CSS file and valid HTML with a viewport meta tag, descriptive page titles and internal links that work at the root of a YOURUSERNAME.github.io site. Create a GitHub Actions workflow that runs python3 build.py, checks that the output includes index.html, then deploys the generated static output with the supported GitHub Pages artifact actions. Explain every file you added. No content-management system and no JavaScript dependency.
Narrator: Ask the agent to run python3 build.py and show any errors. If you are using Claude Code locally, open the finished output with python3 -m http.server 8000 --directory docs (or whichever output folder it chose), then visit http://localhost:8000/. If you are using a cloud coding agent, request a preview or inspect the generated output and pull request before merging.
Narrator: Step three: put it online with GitHub Pages
Narrator: In GitHub, make sure your proposed files are committed or your coding agent's pull request has been reviewed and merged into main.
Narrator: Open your repository's Settings, then Pages.
Narrator: Under Build and deployment, select GitHub Actions as the source, because your workflow needs to run Python before the finished HTML exists.
Narrator: Open the repository's Actions tab. Watch the build and deployment. A green check is encouraging; a red failure is a request to investigate, not to pretend the site launched.
Narrator: Visit https://YOURUSERNAME.github.io/. Open a full article. Try it on your phone. Follow the archive link. If it fails, give the coding assistant the exact error from GitHub Actions.
Narrator: GitHub Pages cannot run a Python web server for each visitor. Your workflow runs Python ahead of publication and sends GitHub Pages the resulting static HTML. This difference is why the site can be cheap, quick, and pleasantly uncomplicated. GitHub also supports publishing a prebuilt docs/ folder from a branch, the method my present repository uses. In that case the output includes .nojekyll, an empty file telling Pages not to run Jekyll over the already generated HTML. Either method can work. Choose one deployment arrangement, and have the agent document it.
Narrator: A custom domain can wait. Once the site works, add a domain in GitHub's Pages settings and configure DNS with your registrar according to GitHub's domain guide. Verify that you own it and turn on HTTPS where available. A personal domain is lovely, though the free github.io address is a perfectly genuine website.
Narrator: The free Cloudflare DNS layer I should have told you about
Narrator: I left out a very practical part of how I run my own websites: Cloudflare. All five of my sites use Cloudflare's free DNS service. I like having my domain settings in a consistent, understandable dashboard. I can point a domain at a new website, add a subdomain, check where mail is supposed to go, and change things without treating every DNS adjustment as a dark ritual. For me, Cloudflare is part of the pleasure of running my own little empire of websites.
Narrator: DNS is an address book for the internet. Your domain is the name people remember; DNS records tell browsers where to find your site and tell mail servers how to handle mail for that name. Paying for a domain registration is separate from paying for DNS hosting, which in Cloudflare's free plan can cost nothing. It is also separate from website hosting: I use Cloudflare for DNS even when the actual pages live on GitHub Pages or another provider. You do not have to use Cloudflare to follow this tutorial, and the free YOURUSERNAME.github.io address needs no purchased domain at all.
Narrator: Domain registration itself still costs money unless somebody offers a genuine promotion. Registrars charge different prices and renewal rates; I would not claim every domain is sold at the same retail markup. Cloudflare Registrar offers supported extensions at registry and ICANN cost without an additional markup. That's a separate product from its free authoritative DNS. You can buy your domain elsewhere and still use Cloudflare DNS for free. If you move registration to Cloudflare Registrar, read its nameserver and registrar rules first.
Narrator: How to point your own domain at GitHub Pages using Cloudflare
Narrator: First, finish publishing the github.io version of the site and make sure it works. Buying a domain is optional.
Narrator: If you do own a domain, make a free Cloudflare account and add the domain. Before changing anything at the registrar, carefully compare every imported DNS record with your existing DNS provider. Preserve mail records such as MX, SPF, DKIM and DMARC, plus any verification records or other services you use.
Narrator: Cloudflare gives you the authoritative nameservers for your zone. If everything was copied correctly, replace the old nameservers at your domain registrar with the ones Cloudflare assigned. Allow time for the change to propagate. If DNSSEC was enabled at the old provider, follow Cloudflare's migration guidance rather than leaving an obsolete DS record in place.
Narrator: In your GitHub repository's Settings → Pages, add the exact custom domain you want. Verify domain ownership if GitHub asks, and consult GitHub's current DNS instructions. For the bare domain, the usual GitHub Pages setup uses four A records at @, pointing to 185.199.108.153, 185.199.109.153, 185.199.110.153 and 185.199.111.153. For www, create a CNAME pointing to YOURUSERNAME.github.io, not a full article URL.
Narrator: In Cloudflare, start the GitHub Pages web records as DNS only, the grey cloud, so you can verify GitHub's domain mapping and HTTPS certificate without a second proxy complicating the test. Cloudflare's orange-cloud proxy is a separate, optional feature with its own HTTPS, caching and security behaviour. You can explore it later, once the site and certificate work, and only if the configuration suits your host.
Narrator: Test both the bare and www addresses. Confirm the intended address is canonical and that GitHub Pages offers HTTPS. Visit the site, click links and make sure email still works. Do not use wildcard GitHub Pages DNS records just to save yourself a few minutes; GitHub warns against them.
Narrator: Once the DNS basics are settled, Cloudflare has all sorts of optional facilities worth exploring as your site grows: redirects, proxying, caching, protection, analytics, edge logic and more. Some are included in free tiers and others are paid or subject to limits. You need not turn any of them on to have a complete website. Free DNS and simple control are the first things I recommend looking at. I have enough of the other toys to investigate later, when there is a genuine problem to solve.

Narrator: Optional: become as persnickety as the proprietor
Narrator: I have taken the simple idea rather far. I told my ChatGPT and Claude friends to be so compliant that their heads would explode, particularly about web standards. Mine is a website that wants to look like 2004 while making a serious effort to satisfy 2026 readers, including people who cannot see the page and people who browse with a keyboard, a screen reader, or Lynx, the text-only browser. A screen-reader test, a keyboard-only test, a reduced-motion check and a text-browser pass reveal different kinds of problems. Passing a static checker is useful; it is not a certification that a site meets every requirement of the ADA or WCAG.
Narrator: The extra equipment includes RSS 2.0, Atom, feed autodiscovery, OPML subscriptions, descriptive alt text, HTML headings in sensible order, accessible labels and landmarks, canonical URLs, a sitemap, robots.txt, honest structured data, author attribution, visible corrections, and human-readable records of changes. I care about image sizes, link integrity, metadata and mobile responsiveness. I run build audits. I consider Core Web Vitals and PageSpeed Insights suggestions as evidence to investigate, not as a magic score whose pursuit should wreck the experience.
Narrator: There is also a wiki, a feed, and rather elaborate machine-readable documentation of the publishing experiment. There are full-text AI-generated illustrations. Most of the published writing is generated by AI at my direction, and the articles disclose the model and the original prompt. Git commits and public handoffs tell readers what happened between versions. I've even developed a house rule about how to spell the possessive of Chris.
Narrator: Creative Commons is another choice to make deliberately. Decide what you own and what you wish to license. A Creative Commons licence chooser can help; a licence applies to material you have rights to license, and licensing your original text needn't mean licensing someone else's photographs, trademarks or quoted material. Add a clear statement specifying which parts of your site the licence covers. A credit and an alt description are not substitutes for permission.
Narrator: Prompt 5: The full restomod inspection. Review this weblog as if it has a 2004 body and a 2026 chassis. Audit keyboard-only navigation, focus visibility, mobile reflow, zoom, screen-reader semantics, colour contrast, reduced motion, missing alt text, heading structure, Lynx/text-only usability and operation without JavaScript. Then check internal links, canonical metadata, RSS and Atom validity, feed autodiscovery, sitemaps, structured data where genuinely justified, robots controls, image optimization and PageSpeed Insights opportunities. Add tests where sensible. Distinguish confirmed failures from suggestions and from things you cannot verify. Make only changes you can explain. Do not claim ADA or WCAG certification, a Lighthouse score, or validated rich results without evidence.

You can make a perfect little weblog with half a dozen pages, tasteful CSS, accessible links, and zero interest in analytics. My site is complicated because I keep giving my assistants jobs and insisting they leave records. It is not complicated because a personal weblog requires that complication.
